## 1. 개요

본 문서는 학원용 문제 제출기 시스템의 **테스트 시나리오**를 정의한다.  
각 시나리오는 사용자/시스템 관점의 흐름으로 묶여 있으며, 상세 조건·단계·기대결과는 [테스트 케이스](test-cases.md)에서 TC-ID로 관리한다.

### 1.1 테스트 유형

| 유형 | 설명 | 주 사용처 |
|------|------|-----------|
| **Unit** | 함수/클래스 단위 검증 | 추출 로직, 파싱, 유틸 |
| **Integration** | DB/스토리지/큐 연동 검증 | 업로드→저장, 검수→DB |
| **API** | REST API 요청/응답 검증 | FastAPI 엔드포인트 |
| **E2E** | 사용자 시나리오 전체 검증 | 업로드→검수→검색→시험지 |
| **Security** | 인증/권한/격리 검증 | RBAC, 조직 격리 |
| **Performance** | 응답 시간·처리량 검증 | 검색, PDF 생성, 추출 |

### 1.2 범위

- **MVP 범위**: 콘텐츠 업로드/추출, 검수, 문항 검색, 시험지 제작(PDF), 인증/RBAC, 감사 로그.
- **로드맵 제외**: 학생 온라인 풀이/채점, HWP 업로드·생성, 유사문항 생성 등은 시나리오에서 제외하거나 별도 섹션으로만 다룬다.

## 2. 인증·권한 시나리오

### 2.1 로그인/토큰

- **TS-AUTH-001**  
  운영자가 이메일/비밀번호로 로그인하면 액세스 토큰을 받고, 30분 만료 시 재인증(또는 리프레시) 유도가 되어야 한다.
- **TS-AUTH-002**  
  잘못된 비밀번호 또는 미가입 이메일로 로그인 요청 시 401 및 명확한 오류 메시지가 반환되어야 한다.
- **TS-AUTH-003**  
  만료된 토큰으로 API 호출 시 401이 반환되고, 재로그인 또는 토큰 갱신 플로우로 유도되어야 한다.

### 2.2 RBAC(역할 기반 접근)

- **TS-AUTH-004**  
  교사가 검수 작업 목록·문항 승인 등 운영자 전용 API를 호출하면 403이 반환되어야 한다.
- **TS-AUTH-005**  
  운영자는 업로드, 검수, 문항 수정, 검수 대기 목록 조회에 모두 접근 가능해야 한다.
- **TS-AUTH-006**  
  조직 A 소속 사용자는 조직 B의 문항·시험지를 조회/수정할 수 없어야 한다(데이터 격리).

### 2.3 비밀번호·프로필

- **TS-AUTH-007**  
  비밀번호 재설정 링크 요청 시 이메일 발송이 트리거되고, 유효한 링크로만 새 비밀번호 설정이 가능해야 한다.
- **TS-AUTH-008**  
  로그인한 사용자가 본인 프로필(이름 등)을 수정하면 DB에 반영되고 이후 조회에 반영되어야 한다.

## 3. 콘텐츠 업로드·추출 시나리오

### 3.1 파일 업로드

- **TS-UPLOAD-001**  
  운영자가 PDF 한 개를 업로드하면 파일 검증(형식, 크기 ≤50MB) 후 S3(또는 대체 스토리지)에 저장되고, `SourceDocument` 레코드가 생성되어야 한다.
- **TS-UPLOAD-002**  
  PNG/JPG 이미지 파일을 다중 선택 업로드하면 각 파일이 검증·저장되고, 문서 단위 메타데이터(제목, 출처, 출제시기) 입력 후 추출 작업이 등록되어야 한다.
- **TS-UPLOAD-003**  
  허용 형식이 아니거나 50MB 초과 파일 업로드 시 400 및 명확한 오류 메시지가 반환되어야 한다.
- **TS-UPLOAD-004**  
  업로드 진행률(또는 상태)이 클라이언트에서 확인 가능해야 한다(프로그레스 바 또는 폴링).

### 3.2 추출 작업

- **TS-EXTRACT-001**  
  업로드 완료 후 추출 작업이 큐에 등록되고, 워커가 PDF→이미지 변환(PyMuPDF, DPI 150)·레이아웃 분석(헤더/푸터/단)·OCR 문항 번호 감지·크롭 저장을 수행해야 한다.
- **TS-EXTRACT-002**  
  작업 목록/상세에서 상태(대기/처리중/완료/실패), 진행률, 처리된 페이지 수, 추출된 문항 수를 확인할 수 있어야 한다.
- **TS-EXTRACT-003**  
  추출 실패 시 오류 메시지가 기록되고, 재시도 시 동일 문서로 새 추출 작업이 등록되어야 한다.
- **TS-EXTRACT-004**  
  *(기존 스크립트 연동)* `extract_problems.py`와 동일한 레이아웃/OCR 파라미터를 사용하는 추출 파이프라인이, 테스트용 PDF 한 페이지에서 기대한 개수만큼 문항을 분할해야 한다.

### 3.3 자동 태깅(LLM)

- **TS-TAG-001**  
  추출된 문항 이미지·텍스트가 LLM 태깅 입력으로 전달되면, 과목/단원/유형/난이도 추정값과(선택) 신뢰도가 저장되고 검수 대기 상태가 되어야 한다.
- **TS-TAG-002**  
  태깅 실패 시 해당 문항은 태그 없이 검수 대기로 두거나, 재시도 정책에 따라 재호출되어야 한다.

## 4. 검수 워크플로우 시나리오

### 4.1 검수 대기·목록

- **TS-REVIEW-001**  
  운영자가 검수 대기 문항 목록을 조회하면, 아직 승인되지 않은 문항만 조직 단위로 필터링되어 반환되고, 썸네일·자동 태깅 요약·필터(과목, 신뢰도)·정렬(최신순, 신뢰도순)이 적용되어야 한다.
- **TS-REVIEW-002**  
  검수 대기 문항 하나를 선택하면 원문 이미지(해당 페이지), 크롭된 문항 이미지, 추출 텍스트, 자동 태깅 결과를 한 화면에서 확인할 수 있어야 한다.

### 4.2 검수 편집·승인

- **TS-REVIEW-003**  
  운영자가 추출 텍스트를 수정하고, 과목/단원/유형/난이도·출제시기·저작권 정보를 입력한 뒤 «승인»을 누르면 문항이 공개(is_public=true)되고, 검수 이력(ReviewHistory)에 변경 내용이 기록되어야 한다.
- **TS-REVIEW-004**  
  «반려» 선택 시 문항은 공개되지 않고, 반려 사유(또는 상태)가 저장되어 목록에서 구분되어야 한다.
- **TS-REVIEW-005**  
  «수정 후 재제출» 또는 이에 상응하는 플로우로 다시 검수 대기 상태로 돌린 뒤, 재검수 후 승인할 수 있어야 한다.

### 4.3 검수 통계

- **TS-REVIEW-006**  
  검수 완료율 대시보드(또는 API)에서 전체 대비 검수 완료 비율, 과목별 완료율, 일별 통계(선택)를 조회할 수 있어야 한다.

### 4.4 문항 삭제·비공개

- **TS-REVIEW-007**  
  운영자가 문항을 삭제(소프트 삭제)하거나 비공개 처리하면, 검색/시험지 추천에서 제외되고, 삭제/비공개 이력이 남아야 한다.
- **TS-REVIEW-008**  
  정책상 30일 이내 삭제 문항은 복구 가능해야 한다(복구 시 소프트 삭제 해제).

## 5. 문항 검색·필터 시나리오

### 5.1 검색 조건·결과

- **TS-SEARCH-001**  
  교사가 과목·단원·유형·난이도·출제시기·키워드를 조건으로 검색하면, is_public인 문항만 조직 단위로 필터링되어 반환되고, 썸네일·지문 일부(최대 200자)·태그가 포함되어야 한다.
- **TS-SEARCH-002**  
  키워드 검색 시 지문·문제·선택지 텍스트(또는 text_content)를 대상으로 매칭되어야 하며, 관련도순/최신순/난이도순/출제시기순 정렬이 가능해야 한다.
- **TS-SEARCH-003**  
  검색 결과는 페이지네이션(기본 20개)으로 제공되고, 빈 조건 또는 조건 불일치 시 빈 목록이 반환되어야 한다.

### 5.2 문항 상세·시험지 추가

- **TS-SEARCH-004**  
  문항 상세 조회 시 전체 이미지, 추출 텍스트, 메타데이터(과목/단원/유형/난이도/출제시기), 출처 정보가 노출되어야 한다.
- **TS-SEARCH-005**  
  교사가 문항 상세에서 «시험지에 추가»를 누르면 현재 작성 중인 시험지(또는 세션)에 해당 문항이 추가되어야 한다.
- **TS-SEARCH-006**  
  검색 조건 저장·재사용(즐겨찾기) 시 동일 조건으로 다시 검색할 수 있어야 한다.

## 6. 시험지 제작 시나리오

### 6.1 조건 설정·문항 선택

- **TS-EXAM-001**  
  교사가 시험지 조건(과목, 단원, 유형, 난이도 범위, 총 문제 수, 난이도 분포)을 입력하면, 조건에 맞는 문항 자동 추천 목록이 반환되어야 한다. 부족 시 알림 또는 빈 목록+메시지가 있어야 한다.
- **TS-EXAM-002**  
  추천/검색 결과에서 문항을 선택·해제하고, 선택된 문항만으로 시험지 초안을 만들 수 있어야 한다. 이미 선택된 문항은 중복 선택되지 않도록 UI/API에서 제한되어야 한다.
- **TS-EXAM-003**  
  선택 문항의 순서 변경(드래그 앤 드롭 또는 순서 API)이 반영되어, 시험지에 반영된 순서로 저장·PDF에 반영되어야 한다.

### 6.2 미리보기·PDF 생성

- **TS-EXAM-004**  
  시험지 미리보기에서 문항 목록(번호, 내용 요약), 난이도 분포, 총 문제 수, 예상 소요 시간을 확인할 수 있어야 한다. 미리보기 단계에서 문항 추가/제거/순서 변경이 가능해야 한다.
- **TS-EXAM-005**  
  «PDF 생성» 요청 시 선택 문항 순서대로 이미지·텍스트가 조합된 PDF가 생성되고, S3 등에 저장된 뒤 다운로드 URL(또는 스트리밍)이 반환되어야 한다. 생성 이력(ExamPaper, ExamPaperItem)이 DB에 남아야 한다.
- **TS-EXAM-006**  
  PDF 레이아웃(페이지 크기, 여백, 폰트) 또는 템플릿을 선택하면, 해당 설정이 반영된 PDF가 생성되어야 한다.
- **TS-EXAM-007**  
  시험지에 포함된 문항의 출처·저작권 정보가 PDF 하단 등에 포함되는 옵션이 동작해야 한다(REQ-071).

### 6.3 성능·한계

- **TS-EXAM-008**  
  일반적인 시험지(예: 20문항) 기준 PDF 생성이 5초 이내에 완료되거나, 대기 시간 동안 진행 상태를 확인할 수 있어야 한다.
- **TS-EXAM-009**  
  총 문제 수 0이거나 문항이 하나도 선택되지 않은 상태에서는 PDF 생성이 거부되고, 명확한 오류 메시지가 반환되어야 한다.

## 7. 데이터·감사 로그 시나리오

### 7.1 조직 격리

- **TS-DATA-001**  
  조직 A 사용자의 문항/시험지/소스 문서 조회·수정·삭제 시, organization_id로 필터링된 데이터만 접근 가능해야 한다.
- **TS-DATA-002**  
  검색·추천·시험지 조립 시 사용되는 문항은 모두 해당 조직 소유이거나, 향후 «공유» 정책이 정의된 경우에만 타 조직 문항이 포함되어야 한다.

### 7.2 감사 로그

- **TS-DATA-003**  
  업로드, 검수 승인/반려, 문항 수정, 시험지 생성, 문항 삭제/비공개 등 중요 작업 발생 시 감사 로그에 사용자·시간·작업 유형·대상 리소스·결과(성공/실패)가 기록되어야 한다.
- **TS-DATA-004**  
  관리자 전용 조회/필터(기간, 사용자, 작업 유형)로 감사 로그를 조회할 수 있어야 한다.

### 7.3 저작권·출처

- **TS-DATA-005**  
  소스 문서·문항에 출처(저작권자, 출판사, 출제기관) 입력이 필수로 검증되고, 미입력 시 저장·승인이 거부되거나 경고되어야 한다.
- **TS-DATA-006**  
  문항별 출처 정보가 검색 결과·문항 상세·시험지 PDF에 노출되어야 한다.

## 8. 비기능(보안·성능) 시나리오

### 8.1 보안

- **TS-NFR-001**  
  API 통신은 HTTPS로만 허용되어야 한다(HTTP는 리다이렉트 또는 차단).
- **TS-NFR-002**  
  로그인·비밀번호 재설정 등 민감 입력은 SQL 인젝션·XSS·CSRF에 노출되지 않아야 하고(ORM·이스케이프·토큰 검증), 파일 업로드는 타입·크기·확장자 검증을 거쳐야 한다.

### 8.2 성능

- **TS-NFR-003**  
  일반적인 다중 조건 검색(과목+난이도 등) 응답이 1초 이내로 반환되어야 한다(캐시 사용 시 캐시 히트 기준).
- **TS-NFR-004**  
  문항 추출(크롭+OCR)은 페이지당 평균 10초 이내, 자동 태깅은 비동기 처리 시 1~5분 이내 완료 목표로 동작해야 한다(부하·큐 대기 시 변동 허용).

### 8.3 가용성·헬스

- **TS-NFR-005**  
  헬스 체크 엔드포인트(예: `/health`)가 DB·Redis·스토리지(선택) 연결 상태를 반영해 200/503을 반환해야 한다.
- **TS-NFR-006**  
  작업 큐(Redis/Celery 등) 장애 시 업로드·추출 요청이 실패하되, 서버는 다운되지 않고 적절한 오류 응답을 반환해야 한다.

## 9. 기존 추출 스크립트(Unit/Integration) 시나리오

현재 `extract_problems.py`에 대응하는 시나리오로, 향후 API·워커에서 동일 로직을 사용할 때 그대로 테스트 코드에 매핑할 수 있다.

### 9.1 페이지 범위 파싱

- **TS-LEGACY-001**  
  `parse_range("all", 10)` → `[1..10]`, `parse_range("1-5", 10)` → `[1,2,3,4,5]`, `parse_range("3", 10)` → `[3]`, `parse_range("99", 10)` → `[10]`(클램핑) 등이 기대대로 동작해야 한다.
- **TS-LEGACY-002**  
  `parse_range("a-b", 10)` 또는 `"1-5-3"` 등 잘못된 형식은 `BadParameter`(또는 동등 예외)를 발생시켜야 한다.

### 9.2 레이아웃·문항 분할

- **TS-LEGACY-003**  
  테스트용 PDF 한 페이지를 입력했을 때, `find_header_footer_lines`·`find_column_divider`가 기대한 y/x 경계를 반환하고, `split_problems_in_column_with_ocr` 결과 블록 개수가 기대 문항 수와 일치(또는 허용 오차 내)해야 한다.
- **TS-LEGACY-004**  
  주어진 페이지 이미지에서 문항 영역으로 크롭한 이미지들이 실제로 한 문항씩만 포함하도록 픽셀 영역이 분할되어야 한다(골든 이미지·영역 좌표 비교 또는 휴리스틱 검증).
